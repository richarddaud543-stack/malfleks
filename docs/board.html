The product

One question, asked at every branch

resolveDeliveryRoute() is four lines long and everything else is downstream of it. It reads one boolean on the branch and decides who carries the box.

Does this branch run its own delivery? branch.deliveryOffered — src/lib/order.ts

Yes → brand fleet

The brand carries it. No courier in the loop, no third-party handoff, and no published ETA — brands don't quote one, so we don't invent one.

6 of 19 branches
or

No → local courier

We match couriers serving that branch's city. Couriers do publish an ETA, so the estimate shown is theirs, not ours.

13 of 19 branches · 5 couriers

Why the answer arrives before the click

The route used to be computed on the delivery page — one page after the customer had already chosen. previewDelivery() now runs the same rule on the search card and the product page, so an unorderable product says so on its own page instead of after the click. Deliberate non-goal: there is no delivery-speed filter. Only couriers publish an ETA, so filtering on speed would silently hide every brand-fleet listing. Show the number; don't filter on one we only have half of.

Working agreement

No assignment begins cold

Every engineer runs the same three phases. The numbering is the actual sequence, and skipping the first one is what the gate exists to prevent.

Phase 0

Onboard

Research current professional standards for your domain on the live web before writing any code. Record findings with real sources. Prefer primary sources and recent material — the stack moves and training data goes stale.

Phase 1

Build

Implement, explicitly applying what Phase 0 established. Where the research changed your approach, say so in the report. Research that contradicts the brief is the most valuable kind.

Phase 2

Record

Write what you learned into your own skill file — a technique that failed, a constraint that wasn't obvious, a number you actually measured. Delete anything that stopped being true.

The gate. Nothing merges to master without its Phase 0 research recorded in the handbook. Ten research reports currently live in docs/research/ — one per discipline, each auditing the real code rather than summarising the web.

Why the skill files exist durable

  • Every engineer starts each assignment with no memory of the last one.
  • Knowledge that lives only in a finished conversation is knowledge the company buys twice.
  • Long-form reasoning goes in docs/research/; the sharp load-bearing specifics go in the skill file.
  • Written for someone competent who has never seen this repo — a measured ratio beats "check contrast".

Integration discipline measured

  • Branches land one at a time, on arrival — never batched.
  • Every branch in the 14 Aug round needed Lead work to be shippable, and none of it showed up inside the branch. It was all seam damage.
  • That's the argument for smaller batches, not for more review.
  • CI runs E2E against a production build, because next dev compiles per request and times specs out under parallel workers.

Architecture

Two stores, one owner each

Prisma owns the catalogue settled

  • The schema is genuinely relational and Firestore has no joins — today's tested invariants would become manually-synced fields.
  • Pages read the database, not the bundled arrays. That cutover landed 17 Aug.
  • src/data is still the editorial source and the seed mirrors it, so the two can drift. parity.test.ts is the interim guard.

Firebase is scoped to Auth, Analytics and saved requests settled

  • No Firestore reads or writes for catalogue data. No second source of truth.
  • Saved order requests are the one exception: user-scoped, not relational, nothing joins them, and the identity that owns them already lives in Firebase.
  • Putting them in SQL would mean mirroring Firebase uids into a second store for no gain.

verified is a first-class column

  • Every branch and courier record says whether it's researched fact or illustrative placeholder.
  • Invented data must never claim verified: true. Provenance is logged in src/data/SOURCES.md.
  • Map coordinates are approximate city-centre points shared by every branch in a city — so adding them deliberately did not flip anyone's flag.
  • Currently 12 of 19 branches and 2 of 5 couriers are verified.

Shape decisions worth knowing

  • priceTZS is an Int — the catalogue spans TZS 32K earbuds to TZS 245M SUVs and floats have no business here.
  • specs and regionsServed became tables, not JSON columns, so they can be queried and constrained.
  • Product.brandId stays denormalised alongside branchId; the seed asserts they agree.
  • Search prices are bucketed into bands, not a slider — a slider across that range is unusable.

Authentication

Client proves identity, server holds the session

Google sign-in only. onAuthStateChanged doesn't exist during SSR, so the client SDK's notion of "signed in" is invisible to a Server Component — the cookie is the only thing a server-rendered page can check.

A Data Access Layer, not a proxy

  • There is no proxy.ts in this repo. The DAL isn't a second layer behind one — it is the only layer, which is why it's authoritative rather than optimistic.
  • Next's own guidance: proxy "should not be your only line of defense" — it runs on prefetches, and a matcher edit can silently drop a route out of coverage.
  • verifySessionCookie(cookie, true) is the revocation-checking form. It costs a round trip per render pass, which is what cache() is for.

Security Rules emulator-tested

  • Default-deny, owner-only reads, and no client writes at all. Every write goes through the Admin SDK, which bypasses rules by design.
  • Ownership is keyed by the path, not a field — a field can be spoofed on the write that creates it; a path segment compared against request.auth.uid cannot.
  • 13 assertions run against the real emulator on their own CI job. Both directions were checked by injecting the two classic mistakes and watching the suite fail.
  • App Check is wired (reCAPTCHA v3) but enforcement is still an unclicked console action.

Contrast is computed, not eyeballed

  • src/lib/accent.ts searches outward from a brand's own colour in both directions and takes the first variant clearing 3:1 — so the correction is the smallest one that works.
  • Not directional by assumption: on the light ground, bright accents fail and lightening them makes it worse. Oraimo tops out at 2.21:1 even at pure white.
  • A border has two neighbours, so it's checked against both. Halotel passes on the page at 3.19:1 and fails inside its own chip at 2.75:1.
  • Brand colours are identity, so four of six brands are returned untouched.

Imagery, and what we won't do

  • Brand logos are real, from Wikimedia Commons, attributed in SOURCES.md.
  • Product imagery is a custom SVG icon set, tinted per brand. Commons searches for generic categories kept surfacing vintage or competitor-branded photos.
  • No scraped product photography. If real photos ever land, they go through next/image with a provenance entry.
  • Motion respects prefers-reduced-motion — including view transitions, which run outside React where useReducedMotion() can't see them.

The one page-to-page relationship worth building

A product's icon tile on a search card and the same product's showcase on its own page are the same object, so they morph across the navigation rather than swapping. React's <ViewTransition> with a shared product-${id} name, scoped to a product-view transition type so an unrelated same-page filter change can't fire it. Native browser API, no new dependency.

Quality

What "done" has to mean

The standing baseline is non-negotiable and predates any individual assignment.

Before any hand-off

  • npx tsc --noEmit, npm run lint, npm test — all clean.
  • Every new page ships page-specific metadata and a sitemap entry.
  • Every new feature ships at least one real behavioural test.
  • Accessibility is part of done: real labels, keyboard operation, announced errors, the global :focus-visible ring left intact.
  • Data provenance via the verified flag.

The lesson that cost the most durable

  • Two bugs escaped the entire test suite and were caught by a human using the page: a skip link that moved scroll but not focus, and a doubled <title>.
  • Both are now guarded across every affected route.
  • Open the page and use it — passing tests are not the same as looking.
  • Mutation testing is on the register precisely because an agent can write a test that trivially passes against the code it just wrote.

Four things engineering can't decide

Each of these is a call that belongs to you, not to an engineer. A number invented here would read as policy to whoever found it next.

Debt #2

A git remote

Needs your GitHub account. It's the register's own "next thing worth doing" — everything lives on one disk today, and CI has never run because it has nowhere to run. Unblocks #1 and #11 at the same time.

Debt #20

A retention policy for customer PII

How long should an untouched saved request live before it expires on its own, and should closing an account purge the subcollection? Customers can delete their own records now, which covers the data-rights half. The mechanism to enforce a retention rule isn't built because the rule doesn't exist yet.

Debt #16

Turn on App Check enforcement

Wired in code, monitor-only in the console — which is Google's recommended sequence. Flipping it to enforcing is a click in the Firebase console that only you can make.
